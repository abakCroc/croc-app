# Plan: Migrate from raw `-buildmode=c-shared` to gomobile

## Previous Approach: Why `-buildmode=c-shared` Failed

### What was built
- `cmd/capi/capi.go` — manual CGO/JNI wrapper exporting `crocStart`, `crocWait`, `crocCancel` via `//export` directives
- `CrocNative.kt` — Kotlin side with `System.loadLibrary("croc")` + `external fun` declarations
- `CrocProcess.kt` — reads croc stderr via pipe FD returned from `crocStart()`
- 3 Gradle Exec tasks building `libcroc.so` for arm64, armeabi-v7a, x86_64 with NDK clang as `CC`

### What worked
- CI built `libcroc.so` successfully (11.3 MB arm64, 12.1 MB x86_64)
- APK contained correct `.so` files with proper ELF format
- `System.loadLibrary("croc")` succeeded — library loaded without `UnsatisfiedLinkError`

### What crashed
**Every run on Android 16 emulator (x86_64):**
```
Fatal signal 6 (SIGABRT), code -6 (SI_TKILL) in tid 7450 (m.dking.crocapp)
Process uptime: 52s
1 total frame in backtrace:
      #00 pc 000000000028d281  libcroc.so
```

### Root cause analysis
- **SIGABRT + SI_TKILL** = process sent `tgkill(pid, pid, SIGABRT)` to itself — this is Go's `runtime.throw()` → `abort()`
- **tid == pid** = crash on the main thread, not on a goroutine thread
- **1 frame in backtrace** = Android unwinder cannot traverse Go stack frames (Go uses its own stack management)
- **Process uptime 52s** = crash happened during a croc operation, not during `System.loadLibrary`

### What was NOT the cause
Attempted fix: replaced 3 `os.Exit(0)` in `cli.go` + 3 `log.Fatalf` in `crypt.go` with safe returns + added `recover()` in goroutine. **Did not help** — crash at same location (offset shifted by only `0xE0` bytes, matching the added code size).

This ruled out `os.Exit()` as the primary cause. The crash is from `runtime.throw()` — an unrecoverable Go runtime internal error that `recover()` cannot catch.

### Actual cause: missing Android runtime initialization
Raw `-buildmode=c-shared` initializes the Go runtime during `dlopen()` via `DT_INIT_ARRAY`. This does NOT perform Android-specific setup that the Go runtime needs:

| What's needed | Raw c-shared | gomobile |
|---|---|---|
| Signal masking on main thread | ❌ | ✅ |
| Dedicated pthread for Go scheduler | ❌ | ✅ |
| Proper `JNI_OnLoad` with runtime init | ❌ (auto-init via DT_INIT_ARRAY) | ✅ |
| `GOTRACEBACK=crash` for debugging | ❌ | ✅ |
| TLS setup for goroutines on Android | ❌ | ✅ |

Without signal masking, Android's ART signal handlers conflict with Go's signal handlers. Without proper thread setup, Go's scheduler deadlocks or throws on thread creation. These manifest as `runtime.throw()` → `SIGABRT`.

### Lesson learned
**Do NOT use raw `-buildmode=c-shared` on Android.** Use gomobile instead — it adds the same `-buildmode=c-shared` under the hood but with proper Android runtime initialization (`x/mobile/internal/mobileinit`). The additional init code is ~200 lines of C/Go that handle signal masking, thread creation, and TLS setup specifically for Android's process model.

## Why gomobile
gomobile uses `-buildmode=c-shared` under the hood but adds:
- Proper signal masking on the main thread
- Dedicated pthread for Go scheduler
- Correct `JNI_OnLoad` with Android runtime init
- `GOTRACEBACK=crash` for debugging

This should fix the `runtime.throw → abort → SIGABRT` crash.

## Architecture: Pipe FD via gomobile

Keep the existing pipe-FD approach to minimize Kotlin changes. The only difference is gomobile generates JNI bridge instead of manual CGO:

```
Kotlin calls Mobile.start(configJson) → returns Long (pipe FD)
Kotlin reads pipe FD line-by-line → parse progress
Kotlin calls Mobile.wait() → returns Long (exit code)
Kotlin calls Mobile.cancel() → signal cancellation
```

## Files Changed

### 1. CREATE: `croc-mobile/croc.go` + `croc-mobile/go.mod` (new Go module in main repo, NOT in submodule)

New Go module in the main repo — gomobile bind target. No CGO, no JNI — gomobile generates that automatically. The croc submodule is NOT modified.

**`croc-mobile/go.mod`:**
```
module com.dking.crocapp.croc

go 1.25

require github.com/schollz/croc/v10 v10.0.0

replace github.com/schollz/croc/v10 => ../third_party/croc-src
```

The `replace` directive points to the local submodule, so gomobile builds against the submodule source without modifying it.

**`croc-mobile/croc.go`:**
```go
package croc

// exports: Start(configJson string) (int, error)
//          Wait() (int, error)
//          Cancel()
```

Ported logic from `cmd/capi/capi.go`:
- JSON config parsing (args, env, workDir)
- `os.Pipe()` for stderr capture
- `cli.Run()` in goroutine with panic recovery
- `runWaitGroup` synchronization
- Return pipe FD from `Start()` (gomobile maps Go `int` → Java `long`)

Key improvements over current capi.go:
- No CGO/JNI boilerplate
- `defer recover()` in goroutine
- Fix double `jstringToUTF` call bug
- Reset state between runs

gomobile maps the API to Java:
```java
// Generated class — name depends on package/module path
// With module "com.dking.crocapp.croc" gomobile generates:
public final class Croc {
    public static long start(String configJson) throws Exception { ... }
    public static long wait() throws Exception { ... }
    public static void cancel() { ... }
}
```

gomobile is run from `croc-mobile/`:
```bash
cd croc-mobile
gomobile bind -target=android -androidapi=26 -o ../app/libs/croc.aar .
```

## os.Exit Risk

The 3 `os.Exit(0)` calls in `cli.go` and 3 `log.Fatalf` in `crypt.go` still exist. These would kill the process if reached. Assessment:

- `cli.go:207` — classic mode wizard. App never uses `--classic`. **Unreachable.**
- `cli.go:448` — send with `CROC_SECRET=""` + `--code` set. App never uses `--code`. **Unreachable.**
- `cli.go:721` — receive with `CROC_SECRET=""` + `--code` set. Same. **Unreachable.**
- `crypt.go:27,43,89` — `rand.Read` failure. **Practically impossible.**

**Decision:** Do NOT patch cli.go/crypt.go. The app's argument construction ensures these paths are never triggered. If a crash still occurs, we can add targeted patches later with evidence.

## Decisions

- **gomobile + Go 1.25**: Try `@latest` first. Fix compatibility issues if they arise.
- **os.Exit in cli.go**: Do NOT patch. All 3 `os.Exit(0)` paths are unreachable with the app's argument construction. Patch later only if crash evidence points to them.

## Risks to Resolve During Implementation

1. **gomobile + vendored deps**: Need to verify `gomobile bind` works with `vendor/` from a module that uses `replace` directives. May need `GOFLAGS=-mod=vendor` or gomobile may not support vendoring at all.
2. **NDK requirement**: gomobile needs NDK for CGO cross-compilation. Keep NDK setup in CI.
3. **gomobile class naming**: The generated Java class name depends on the Go module path (`com.dking.crocapp.croc` → class `Croc`). Verify no conflict with existing `CrocNative.kt` (which will be deleted before build).
4. **AAR ABI split**: By default `gomobile bind -target=android` builds arm, arm64, x86, x86_64. We only need arm64, armeabi-v7a, x86_64. Filter with `-target=android/arm64,android/arm,android/x86_64`.
